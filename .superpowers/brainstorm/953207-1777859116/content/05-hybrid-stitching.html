Hybrid Stitching — Each Layer Does What It's Best At

Not A or B or C. All three, each at the moment they're strongest.

The problem with picking one

Agent-only

Burns tokens on mechanical assembly every time a slide changes. The agent is a writer, not a compiler.

Web-app-only

Works for preview but can't produce a real deck.html for slidify or external sharing. The web app is a viewer, not an assembler.

Daemon-only

File watcher adds latency and complexity. Rebuild-on-every-change is noisy when the agent is writing 6 slides in sequence.

The hybrid: each layer at the right moment

AGENT writes fragments
Authoring phase — agent writes what it's good at
The agent writes deck-plan.json, theme.css, and individual slides/*.html fragments. It never assembles. It never writes deck.html. Each slide is ~100 lines of pure content. The agent's token budget goes to design quality, not file plumbing.
agent → Write("deck/slides/03-solution.html", "<section>...</section>")
agent → Write("deck/deck-plan.json", { slides: [..., {id:"s3", file:"slides/03-solution.html", status:"ready"}] })
WEB APP stitches for preview
Preview phase — web app shows what it's good at
The web app reads deck-plan.json, fetches each slide file via the project file API, and builds a live srcdoc by injecting theme.css + framework.js + slide sections into the iframe. Instant preview. No round-trip. No file write. The user sees every slide update the moment the agent finishes writing the fragment.
webapp → fetch("/api/projects/{id}/files/deck/deck-plan.json")
webapp → fetch each slide file referenced in plan.slides[].file
webapp → buildDeckSrcdoc(theme, framework, slideFragments)
webapp → iframe.srcdoc = stitchedHtml
DAEMON assembles for export
Export phase — daemon produces what slidify needs
When the user clicks "Export to PPTX", the daemon reads deck-plan.json, reads all slide fragments, and writes a final deck.html — a real file on disk with all sections inlined, theme embedded, framework included. This is the artifact slidify converts. It only gets built once, at export time. Not on every edit.
daemon → POST /api/projects/{id}/deck/assemble
daemon → read deck-plan.json + theme.css + framework.js + all slides/*.html
daemon → write deck/deck.html (complete, self-contained)
daemon → exec slidify convert deck/deck.html --output deck.pptx
daemon → return { pptx: "deck/deck.pptx", fidelity: [...] }
AGENT repairs fidelity issues
Post-export phase — agent fixes what slidify flagged
After export, the daemon returns a fidelity report: which slides converted natively, which got rasterized, which had overflow or missing fonts. The agent reads this report and surgically fixes individual slide fragments — replacing backdrop-filter with a solid gradient, adding data-pptx-role hints, or simplifying a layout that exceeds slidify's capabilities. Then the daemon re-exports.
agent → Read fidelity report from deck-plan.json.slidify.fidelityIssues
agent → Edit("deck/slides/04-architecture.html") — fix rasterized gradient
agent → Update deck-plan.json.slides[3].status = "fixed"
user → clicks "Re-export" → daemon reassembles + slidify converts again

Why this hybrid is correct

Each layer does one job
Agent Authors content fragments + theme
Web app Live preview via srcdoc stitching
Daemon Assembles deck.html for export
Agent (repair) Fixes slidify fidelity issues
Token budget goes to quality
Tokens on assembly 0
Tokens on design per slide 100%
Files in agent context ~200 lines (theme + 1 slide)
Rebuild latency 0ms (web app stitches live)

The principle: Write once (agent fragments) → view instantly (web app srcdoc) → materialize on demand (daemon assembly) → repair surgically (agent fidelity fixes). No layer duplicates another layer's work. The deck.html file only exists when something outside the web app needs it (slidify, PDF export, external sharing).
