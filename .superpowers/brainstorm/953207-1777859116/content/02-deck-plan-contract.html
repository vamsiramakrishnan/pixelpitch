What should the deck-plan.json contract look like?

This file is the single source of truth between the agent and the web app. It drives which UI phase the workspace shows and what content populates each component.

Proposed Schema

deck-plan.json
{ "version": 1, "phase": "narrative" | "structure" | "generating" | "ready" | "exporting", "title": "Q3 APAC AI Practice Review", "audience": "VP Engineering + Regional Leads", "theme": "tech-sharing", "designSystem": "google-cloud", "narrative": { "beats": [ { "id": "b1", "label": "Context", "summary": "APAC AI practice scale and scope" }, { "id": "b2", "label": "Problem", "summary": "Customer latency during peak inference" }, { "id": "b3", "label": "Solution", "summary": "Vertex AI traffic-splitting endpoints" }, { "id": "b4", "label": "Evidence", "summary": "Reference deployment: 40% latency drop" }, { "id": "b5", "label": "Architecture", "summary": "Multi-region serving diagram" }, { "id": "b6", "label": "Timeline", "summary": "6-week implementation plan" }, { "id": "b7", "label": "Ask", "summary": "Approve POC budget" } ] }, "slides": [ { "id": "s1", "beatId": "b1", "type": "title", "title": "APAC AI Practice — Q3 Review", "file": "slide-01-title.html", "status": "ready", "speakerNotes": "Welcome everyone, today we're covering..." }, { "id": "s2", "beatId": "b2", "type": "content", "title": "The Latency Challenge", "file": "slide-02-problem.html", "status": "generating", "speakerNotes": "" } ], "slidify": { "lastExport": null, "fidelityIssues": [] } }

How phase drives the UI

phase: "narrative"

Web app shows Outline Editor — editable beat list with drag-reorder. Chat scoped to "help me build the story." No slides yet.

phase: "structure"

Web app shows Slide Planner — beats mapped to slide cards. User assigns types (title, content, data, image). Agent suggests slide count and flow.

phase: "generating"

Web app shows Slide Sorter with live thumbnails. Each slide file generates in sequence. Status badges: ready / generating / pending.

phase: "ready"

Web app shows Deck Workspace — thumbnail strip + full preview + per-slide chat. Click a slide to scope the chat. Arrow keys navigate. Edit any slide individually.

phase: "exporting"

Web app shows Export Panel — slidify progress, fidelity report, download button. Shows which slides convert natively vs. rasterize.

Key design decisions

A

One HTML file per slide

Each slide is slide-01-title.html, slide-02-problem.html, etc. The agent generates them individually. The web app stitches them into a preview deck. Slidify converts each independently.

Enables: per-slide chat scoping, parallel generation, granular slidify fidelity reports, individual slide regeneration without touching others.

B

Single deck.html with section markers

One file with <section class="slide" id="s1"> markers. The agent edits sections in place. The web app parses sections for the sorter/editor.

Enables: shared CSS across slides, framework skeleton stays intact, existing deck rendering "just works", simpler file management.

Recommendation: Option B (single file with section markers). The existing deck framework is load-bearing — it handles scaling, navigation, print layout, and keyboard events. Splitting into per-slide files means re-implementing all of that, plus a stitcher. The web app can parse <section class="slide"> markers to populate the sorter and scope edits, while the agent keeps writing to one file with the proven skeleton.
