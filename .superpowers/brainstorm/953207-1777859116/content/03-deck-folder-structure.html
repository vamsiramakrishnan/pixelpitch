Shared theme + modular slides per deck. The agent writes small, focused files. The web app stitches them for preview.

What each file does
deck-plan.json
Contract between agent and UI. Phase, narrative beats, slide manifest, export state.
theme.css
Design system tokens bound to :root. Shared across all slides. One source of truth for colors, fonts, spacing.
framework.js
Nav, keyboard, scaling, print layout. Injected by deck.html. Never touched by the agent after init.
deck.html
Shell that loads theme.css + framework.js, then inlines each slide's HTML as <section> blocks. Auto-generated from deck-plan.json — the web app or agent rebuilds it when slides change.
slides/*.html
Pure content fragments. No <html>, no <head>. Just the <section class="slide"> interior. ~50-150 lines each.

How it plays with the agent's context window

~2,400
lines in a single-file 12-slide deck
~120
lines per slide fragment
~80
lines for theme.css

Per-slide editing: agent reads theme.css (80 lines) + one slide (120 lines) = 200 lines in context. Not 2,400.

How the stitching works

A

Agent rebuilds deck.html

When slides change, the agent reads deck-plan.json, reads each slide file, and writes a fresh deck.html that inlines them as <section> blocks wrapped in the framework shell.

Simple, explicit, works with existing artifact mechanism. But burns agent tokens on mechanical assembly.

B

Web app stitches at preview time

The web app reads deck-plan.json, fetches each slide file, and builds the srcdoc dynamically — injecting theme.css + framework.js + slide sections into the iframe. No deck.html file needed during authoring. Agent only writes slide fragments + theme + plan.

Zero token waste on assembly. Web app always shows latest state. deck.html only gets built at export time (for slidify).

C

Daemon auto-assembles on file change

The daemon watches deck-plan.json and slide files. When any changes, it auto-rebuilds deck.html. The web app just previews deck.html like any other HTML artifact. Agent writes fragments, daemon assembles, web app previews.

Clean separation: agent authors, daemon assembles, web app renders. But adds a file watcher to the daemon.

Recommendation: Option B (web app stitches at preview time). The web app already builds srcdoc for iframes — extending it to stitch slide fragments from deck-plan.json is natural. The agent never wastes tokens on mechanical assembly. deck.html only gets materialized at export time when slidify needs a real file to convert.
