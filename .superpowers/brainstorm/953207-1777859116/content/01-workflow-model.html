How should the deck authoring workflow surface in the UI?

The skill needs to produce structured output that the web app renders as interactive screens. This decides the interaction architecture.

A

Multi-Phase Chat Protocol

The agent drives the workflow through question forms. Each phase (narrative → structure → generation) is a structured question form the user fills out in the chat pane. The preview pane shows the evolving deck.

Pros

  • Works with existing QuestionForm mechanism — no new web components needed
  • Agent controls the pace and can adapt based on responses
  • Familiar chat-first experience

Cons

  • Outline/structure editing is constrained to form fields
  • No spatial manipulation (can't drag-reorder slides)
  • History of forms clutters the chat log
B

Structured Artifact with Embedded UI

The agent emits a special artifact (e.g., <artifact type="deck-workspace">) that renders as a full interactive workspace inside the preview iframe — with outline panel, slide sorter, and per-slide editing. The iframe communicates with the host via postMessage.

Pros

  • Rich spatial UI: drag-reorder, inline editing, thumbnails
  • Self-contained — the artifact IS the workspace
  • Works within existing artifact streaming mechanism

Cons

  • Complex iframe-hosted app — state sync between iframe and host is fragile
  • The "artifact" is a tool, not a document — conceptual mismatch
  • Hard to version/persist meaningfully as a project file
C

Native Web Components + Agent Protocol

Build new React components in the web app (SlideOutline, SlideSorter, SlideEditor) that render based on structured JSON the agent writes to project files. The agent writes deck-plan.json (outline), generates individual slide-*.html files, and the web app renders a deck-specific workspace with a thumbnail strip, per-slide preview, and scoped chat.

Pros

  • First-class React components — full keyboard nav, drag-drop, accessibility
  • Each slide is its own file — clean per-slide chat scoping
  • deck-plan.json is the structured contract between agent and UI
  • Slidify can convert individual slides or the whole deck

Cons

  • Requires new web components (SlideOutline, SlideSorter, SlideEditor)
  • Requires new daemon endpoints or file-watching for deck-plan.json
  • Most engineering effort

Recommendation: Option C gives us the best foundation for the slide authoring UX you described. The deck-plan.json contract is the key mechanism — it's what lets the agent and the UI stay in sync across the narrative → structure → generation → polish phases. Options A and B try to shoehorn a spatial workflow into chat or iframe, which works for demos but breaks for real slide editing.
